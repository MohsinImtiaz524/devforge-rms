# Tip Analytics

The Analytics Moon exposes `GET /api/analytics/monthly-tips?month=2&year=2024`, backed by the Tips module's public `monthlyAnalytics` read service. Both Analytics React entry points use the existing shared monthly panel, navigation, month/year selection, table controls, loading skeleton, empty state, retry, and session-expiry handling. No charts are added.

The endpoint requires authentication, `analytics.view`, and the session business ID. Existing global membership and Moon/API access checks remain in force. A query-string business ID cannot change the business scope. There are no writes, transactions, approval transitions, migrations, or changes to existing tip collection, receipts, shifts, or payroll.

The source of truth is `sale_tips`: one immutable collection per business/order. Both checkout and standalone collections count once. `sales.tip_amount` is a mirrored amount and is never added again. Monthly filtering uses `collected_at`, not the order creation date or shift date. PostgreSQL applies the business reporting timezone (Asia/Karachi by default); SQLite normalizes its UTC timestamps to the existing Asia/Karachi tip reporting convention. Bounds include the start of the month and exclude the start of the next month.

The only recorded staff assignment is `sale_tips.collected_by`. There is no recipient allocation or shared-tip distribution ledger in this application. The panel explicitly describes collector-based attribution; it cannot report unrecorded payouts or distributions. Staff names prefer the linked business-scoped staff profile, falling back to the business-scoped user name. Missing/moved users retain their amounts under a former-staff label. Inactive staff are included. Grouping uses the collector ID, so equal employee names remain separate.

The table also includes all current business waiter accounts, including accounts with no collections in the selected month, with zero count and PKR 0.00. Waiters are identified by legacy waiter/order-taker roles or an assigned Waiter role; role checks are business-scoped. Multiple assigned roles do not duplicate a waiter. Other staff with recorded collections remain visible. Historical months use the current waiter roster because role history is not versioned. Zero rows do not affect monthly totals and cannot become Top Recipient when there are no tips.

KPIs and table rows come from one grouped ledger query, preventing collection fan-out. Total Tips sums integer cents; Tips Received counts collection rows. Staff amounts/counts reconcile to those totals. Top Recipient is the recorded collector with the highest sum; ties use name and user ID for stable results. Amounts display in PKR with two decimal places. Search, sorting, 20-row pagination, and export retain the complete monthly KPI scope; CSV exports all matching rows and identifies the currency.

Verification includes isolated SQLite tests for boundaries, historical empty months, checkout/standalone counting, exact cents, concurrent/repeated reads, duplicate constraints, cross-business staff isolation, and database failure recovery. HTTP tests cover authentication, permission denial, missing business scope, and invalid filters. Browser tests cover navigation, month/year selection, search, sorting, pagination, export, empty/error/retry states, and mobile overflow. Production PostgreSQL timing and live-data reconciliation remain release checks. Deploy through the normal application release; no database migration is needed.

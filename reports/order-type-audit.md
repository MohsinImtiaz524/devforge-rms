# Shop order type audit

Read-only audit for adding enabled order types to Shop Settings. No application changes made for this feature.

## Confirmed findings

- Canonical types and normalization: services/OrderTypePermissionService.js. Supports dine_in, takeaway, delivery, walk_in; accepts JSON and comma-separated storage; empty/invalid stored selections fall back to restaurant defaults. Retail and mixed shops always have walk_in appended.
- Existing persistence: services/ShopService.js validates nonempty enum arrays on create/update. routes/shops.js exposes superadmin management. public/js/hierarchy.js has hardcoded wizard defaults and service checkboxes.
- Shop settings gap: routes/shop-settings.js does not select or accept allowed_order_types. Existing settings update uses authentication, admin guard, permission policy and session shop scope. public/js/app.js profile settings has no order type controls.
- AuthService.getProfile loads normalized types; routes/auth.js /me refreshes profile. POS uses a loaded user snapshot, so changing settings needs UI refresh handling; backend checks the current database.
- Backend enforcement: services/SalesService.js createSale and updateSaleItems both assert the requested type is enabled. The edit assertion happens before loading the existing sale. Disabling a type therefore blocks item updates on existing orders of that type.
- Both POS implementations filter a hardcoded supported list by the profile configuration, with separate fallback defaults. React disables type switching while editing and also validates the selected type against enabled types on submission.
- Historical order filters contain fixed lists; these should retain access to disabled types. Register payments only lists three types, omits Walk-in, and its context helper treats non-dine-in/non-delivery as Takeaway.
- Kitchen excludes walk_in at query level; kitchen filter intentionally lists restaurant types only. Keep distinct from a missing Walk-in filter in historical payments.
- Type-specific workflows: dine_in table occupancy and waiter assignment; takeaway tokens and handover; delivery address/riders/charges/payment collection; retail or walk_in sale/payment behavior and kitchen exclusion.
- Assignment helper utils/assert-order-assignment.js has a three-type allowlist and delivery-specific staff roles.
- Receipts use repeated label mappings; ESC/POS mapping treats unrecognized values as Delivery. Analytics has duplicated channel labels and missing-value dine_in defaults; AI analysis explicitly looks for dine_in.
- Reporting, shift history, logs, tips and waste read stored types. Disabling a type must not rewrite these records or hide historical access.
- Database schema and startup migrations use comma-separated restaurant defaults for shops and dine_in defaults for sales. Existing schema can store the requested setting; no new column is necessary.
- Website Moon search found no order_type/allowed_order_types integration. Do not assume its menu/contact flow uses the POS type enforcement.

## Implementation implications

1. Expose validated, tenant-scoped allowed types through existing Shop Settings API and UI.
2. Resolve retail Walk-in auto-add behavior explicitly before allowing it to be unchecked.
3. Apply disabled types to new orders and type changes while allowing existing orders to finish under their stored type.
4. Refresh current POS configuration after save; retain server-side validation for stale clients.
5. Preserve historical filters and reports. Fix missing or misleading labels separately where needed.
6. Test invalid/empty/duplicate selections, authorization, cross-shop isolation, legacy defaults, retail behavior, stale clients, existing-order edits, and unchanged printing/payment flows.
